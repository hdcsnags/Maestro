## 1. The architectural decision

**Verdict: MaestroClaw becomes a thin capability broker / policy-and-audit boundary. It does NOT become a hardened custom PTY or a hardened custom security kernel.** This adopts the full audit's Section N recommendation over my own earlier (`-fable.md`) instinct to rebuild the PTY, and over Sol's framing of the allowlist as something to "redesign" into a real capability boundary.

**Reasoning:**

The full audit's core observation is the one that resolves this: Maestro is three products stapled together, and the local terminal/security/runtime layer is "the largest risk and most commoditized" of the three. Every native harness MaestroClaw wraps (Codex 0.147.0, Claude Code 2.1.233, Gemini CLI 0.49.0, Copilot CLI 1.0.80) now ships its own sandbox, its own session/resume, its own permission policy — capabilities that did not exist when the PTY/allowlist "ThamosClaw Kernel" was designed. Building a better version of what the ecosystem now does natively is exactly the trap the full audit calls out: it is a security-critical surface (attackers get to shell metacharacters and path traversal for free if we get it wrong) that we would be maintaining in perpetuity against a moving target (four+ CLIs' argv surfaces, each independently versioned), when the win condition — "an untrusted, prompt-injected model cannot escape the workspace or exfiltrate the host" — is something the harness vendors are now funding full-time and MaestroClaw is not.

That said, **this does not mean "do nothing."** Reading the actual code surfaced a set of bugs that are MaestroClaw's own responsibility under *either* strategic direction — they live in the parts of the system everyone agrees MaestroClaw keeps owning (queue/lease bookkeeping, workspace path handling, the two raw-shell adapters), not in the part being deprecated. A path-traversal bug in `cleanForRetry()` doesn't get safer because we've decided to deprecate the PTY — it needs fixing regardless. So the real shape of the decision is:

| Responsibility | Verdict | What that means concretely |
|---|---|---|
| Queue/lease/executor identity, job lifecycle | **KEEP, HARDEN** | Already reasonably solid; fix the lifecycle bugs in §3 |
| Workspace/artifact path containment | **KEEP, HARDEN NOW** | This is squarely MaestroClaw's job under any architecture — §2 items 1-4 |
| Shell command parsing/allowlist (`shell-analyzer.ts`) | **KEEP as defense-in-depth for the two raw-shell adapters only — do NOT market it as a security boundary for AI adapters, do NOT invest in making it a full capability-policy engine** | Fix the concrete Windows bypass (§2 item 5); do not build "argument-level policy" — that's the reimplementation trap |
| Interactive PTY (`pty-shell.ts`) | **DEPRECATE the interactivity claim; keep as a thin one-shot shell variant sharing approved-shell's execution core** | No rebuild into a real bidirectional terminal. Native harnesses have sessions now — that's where "watch an agent work interactively" should live going forward |
| FS/network sandboxing during AI-adapter execution | **DELEGATE to each CLI's native sandbox flags, going forward** | MaestroClaw's job is to *invoke* the native sandbox flag correctly and *verify* it's active, not to substitute its own. This is why the adapter-currency sprint (§4, Sprint 1) explicitly includes wiring `--sandbox workspace-write` (Codex), `--sandbox` (Gemini), etc. — that IS the delegation, executed as concrete adapter work, not a separate initiative |
| Outer OS/container isolation | **OWNER DECISION, not coded in this pass** | The full audit is right that native sandbox + MaestroClaw's own checks still don't equal a real trust boundary without an outer container/VM. That's an infrastructure decision for Michael (run the whole worker in a VM/container), not something to bolt onto `packages/maestroclaw` source. Flagged, not built, here |
| Env var exposure to child processes | **KEEP, HARDEN NOW** | Every adapter currently does `env: {...process.env}`. This is pure MaestroClaw responsibility regardless of sandbox strategy — fixed in §2 item 6 |

**Where I overrule my own earlier assessment:** `MAESTROCLAW-ASSESSMENT-fable.md` said the PTY "needs a real rework." Having now read the full-project audit and the actual `Adapter` interface (`src/adapters/types.ts` — `run()` takes a prompt string and returns a promise; there is no bidirectional channel and no session handle), I agree with the full audit: building that bidirectional channel is a multi-week interface change to resurrect a capability (drive `vim`/`htop` interactively) that native harnesses now provide better, natively, with resume. Not worth it. Deprecate the claim, keep the one-shot execution, move on.

**Where I weight Sol over Fable on a factual disagreement:** Sol's citations are more current and I defer to them everywhere the two disagreed:
- Codex `--full-auto` is the deprecated flag (not `--ephemeral`, which Sol confirms is real and current — it only controls rollout-file persistence). `codex-cli.ts` line 110 uses `--full-auto`; it should be `--sandbox workspace-write --ask-for-approval never` (Sprint 1).
- Gemini `--yolo` → `--approval-mode=yolo` is the current spelling (`gemini-cli.ts` line 116) (Sprint 1).
- Claude session mode is missing `--print`/`-p` (`claude-code.ts` line 207, `runSessionWithModel`) — confirmed by reading the code: it spawns bare `claude --dangerously-skip-permissions --model <m>` and pipes a prompt into stdin with no TTY. Both audits agree this is broken; Sol adds the citation that `--dangerously-skip-permissions` is documented as unsafe outside an isolated environment, which is exactly the "delegate to native sandbox, but attest it" framing above (Sprint 1).

## 2. What I (Fable) am coding myself now

These are the pieces that are either (a) genuinely architectural — a shared trust-boundary utility used everywhere, not a local patch, or (b) security-critical enough that I want to own the review-quality bar myself before handing follow-on work to Sonnet. All are scoped to `packages/maestroclaw/src/**`; nothing in the Supabase/edge layer is touched by me (see §5 — that's flagged for a separate sprint on a separate surface).

1. **New shared path-containment utility** (`src/lib/path-guard.ts`) — `resolveContained()` (lexical resolve+prefix check) and `resolveContainedRealpath()` (also resolves symlinks on the nearest existing ancestor and re-validates, closing the symlink-escape gap Sol flagged in `resolveSafeArtifactPath()`). One function, used everywhere, instead of four ad-hoc copies of the same check with different gaps.
2. **`src/executor.ts` — `cleanForRetry()` (line 381)**: currently `resolve(workDir, targetPath)` then `unlinkSync()` with **no containment check at all**, where `targetPath = job.allowed_paths?.[0]`. A job record with `allowed_paths: ["../../something"]` deletes outside the workspace. Fix: route through `resolveContainedRealpath`, skip (don't throw — this is best-effort cleanup) on escape, and report an incident.
3. **`src/executor.ts` — `resolveSafeArtifactPath()` (line 32)**: upgrade from lexical-only containment to `resolveContainedRealpath`, closing the symlink-parent gap Sol identified.
4. **`src/iteration/runner.ts` — `buildQueryPrompt()` (line 799) and `readFilesInScope()` (line 649-673)**: both do `join(workDir, relPath)` / `resolve(resolvedWorkDir, relPath)` then `readFileSync` with no containment check, where the paths come from **model-generated `agent_query.files`** and from `loop.scope_paths` respectively. This is the most serious bug in the whole package — a prompt-injected model can make MaestroClaw *itself* read arbitrary host files and forward the contents to a peer adapter. Fix: route both through `resolveContainedRealpath`, skip escaping entries, report an incident when `agent_query.files` specifically tries to escape (that's a stronger signal of injection than a scope-path config issue).
5. **`src/iteration/apply-diff.ts` — `matchesAnyScope()`**: today, a scope of `"**"` (the default) matches literally any string, including `../../etc/passwd`, because glob matching never checks for traversal. Add an explicit `isPathEscaping()` check in `applyDiffWithCheckpoint()` that rejects any diff-touched path containing `..` segments or an absolute/drive-letter root, **independent of scope-glob matching** — the "you may touch anything" scope should still mean "anything inside the workspace," never "anything the OS can resolve to."
6. **`src/lib/kernel/shell-analyzer.ts` — the Windows `#`-comment bypass**: `isShellCommentStart()` currently strips everything after `#` as a comment on **every** platform, but `approved-shell.ts`/`pty-shell.ts` execute via `cmd.exe` on Windows (`shell: true`), and `cmd.exe` does not treat `#` as a comment. `git status # & disallowed-command` parses as a safe one-segment `git` command (everything after `#` is discarded by the analyzer) but `cmd.exe` executes the whole line, including the `&`-joined second command. Fix: gate comment-start detection behind `!isWindows` so the analyzer's view of the string matches what the real interpreter will actually do.
7. **New shared env-scrubbing helper** (`src/lib/child-env.ts`) — every adapter and shell today does `env: { ...process.env }`, handing the executor's own Supabase URL/keys, `EXECUTOR_TOKEN`, and any other secret in the worker's environment to every spawned CLI (and, transitively, to any tool call or shell command that CLI's agent decides to run). `buildChildEnv()` deny-lists `SUPABASE_*`, `EXECUTOR_TOKEN`, `MAESTRO_*`, `APPROVAL_TOKEN*`, and anything matching `*_TOKEN`/`*_SECRET`/`*_API_KEY`, while explicitly allowing the handful of non-secret `CLAW_*` model-override config vars adapters already read. Wired into all seven spawn sites: `claude-code.ts` (both run paths), `codex-cli.ts`, `gemini-cli.ts`, `copilot-cli.ts`, `approved-shell.ts`, `pty-shell.ts`, `command.ts`'s PowerShell resolution, and `iteration/runner.ts`'s `runVerificationWithAbortWatch` (which today doesn't even pass an `env` override, so it silently inherits the full worker environment).
8. **Merge `approved-shell.ts` and `pty-shell.ts` onto one shared allowlist** — today they each define their own `TRUSTED_COMMANDS` set and have already drifted (`pty-shell.ts` adds `top`/`htop`/`vim`/`nano`). Single source of truth in `src/lib/kernel/shell-analyzer.ts` (or a new `trusted-commands.ts`). While in there: **remove `top`/`htop`/`vim`/`nano`** from the trusted set entirely — both audits independently confirmed these have no input path and will simply hang until timeout; keeping them on the allowlist is pure liability with zero working functionality behind it. Relabel `PtyShellAdapter`'s doc comment to stop claiming "high-fidelity interactive terminal sessions" — it is a one-shot command runner with ANSI-aware output capture, not a terminal.
9. **Direct-argv execution for single-segment shell commands — investigated, initially deferred, then shipped once de-risked.** First pass: I found a concrete reason NOT to ship a naive version — `resolveCliInvocation("npm")` on Windows can return a raw `.cmd`/`.ps1` shim path with no interpreter, and modern Node.js (post CVE-2024-27980) refuses to `spawn()` a `.cmd`/`.bat` file directly with `shell:false`, throwing `EINVAL`. Confirmed this empirically on a real Windows box before writing a line of the fix (`spawn('C:\...\npm.cmd', [], {shell:false})` → `EINVAL`, reproduced exactly). Hand-rolling a `cmd.exe /c` wrapper to work around this would risk reintroducing the exact Windows argument-escaping vulnerability class CVE-2024-27980 was about — not something to improvise. Instead: added `cross-spawn` (a small, extremely widely-used, security-audited dependency — the standard fix for exactly this problem) and used it for the single-segment case in `approved-shell.ts` only. Verified against real installed `npm`/`git` on the actual target machine: `npm --version` (the specific case that would have broken) now succeeds via direct argv with no shell reinterpretation at all. Multi-segment pipelines (`|`/`&&`/`||`) are unchanged — still `shell:true` against the raw string, now with the corrected token/separator handling from items 6 and 10. See `test/approved-shell.test.ts`.
10. **NEW finding, not in either original audit: `;` is not a command separator in `cmd.exe` at all.** Found while writing the regression test for item 9 — empirically confirmed `spawn('git status; git status', {shell:true})` on Windows passes the whole string through as ONE literal command line (`git` receives `"status;"` as a malformed first argument and errors immediately; the second `git status` never runs). This is the same bug *class* as item 6 (`#`) — the analyzer's model of "safe separator" didn't match what `cmd.exe` actually does with it — but a different severity: since `cmd.exe` never re-dispatches on `;` at all, there's no way for a second program to execute, so this was "silently broken" rather than "silently unsafe." Still worth rejecting outright rather than leaving a security-relevant "validated as 2 safe segments" claim that doesn't match reality. Fix: `;` is now rejected on Windows with a message pointing at `&&` (which is cmd.exe-native and unaffected). `|`, `&&`, `||` were individually verified empirically to work correctly through `cmd.exe` before concluding `;` was the only broken one — see `shell-analyzer.ts` and its test file for the full empirical trail.

I will make these changes as a small number of focused diffs, one concern per file group, so Michael's review stays easy (per the instruction to keep the `packages/maestroclaw` diff clean and reviewable).

### Sprint 5 — Executor/session job-lifecycle correctness — **DONE** (Sonnet), reviewed by Fable
Surface: `packages/maestroclaw/src/executor.ts`, `src/config.ts`, `src/index.ts`. All three shipped, diff stayed isolated from concurrent §2/Sprint 1/4 work as planned:
- `pass1.success` is now checked. A `pass1FailureNote` is threaded through: logged, reported as a stderr event, folded into the final `result_summary`, and — the part that matters most — it now *also triggers the fix pass* even when `expected_files` were technically all present, since a crash can leave files that look complete but aren't. `buildFixPassPrompt()` got a distinct framing for "nothing officially missing, but pass 1 didn't exit cleanly" instead of a confusing empty `MISSING:` block.

## 8. Eliana read-only proof workload — executed (2026-08-17)

Michael's explicit go-ahead: *"go ahead and use Maestro on Eliana, read-only for now."* This section documents what was actually built and run, not just planned.

### Design

- **Local test, not the live hosted Supabase queue, by deliberate choice.** What's uncertain here is "does routing this kind of task through MaestroClaw's actual adapter-execution core produce a comparable-quality result to manual review" — answering that doesn't need the web → edge-function → executor-api round trip, and skipping it means zero risk to the real hosted job queue and zero new credentials/surface area for a first test. A live end-to-end demo is a clean, separate follow-up if this proves out (it did — see below).
- **New script:** `packages/maestroclaw/scripts/eliana-readonly-review.ts` — a real, runnable, reusable harness (not a throwaway), documented in full in its own header comment. It: clones the real `Elianas Rhythm` project (`C:\New folder\Elianas RhythmMigrate\Elianas Rhythm`) with `--no-hardlinks` (on NTFS a hardlink shares the same data blocks — copy-on-write is not guaranteed the way it is on some filesystems — so this is a deliberate, paranoid choice to guarantee the clone is a real independent copy) into a disposable scratch directory; loads the first 10 of the 72 entries in `app/src/main/assets/studies/votd_calendar.json`; builds an independent review prompt (not primed with any existing manual review); runs it through two adapters with two different read-only enforcement mechanisms; and verifies, after each run, that nothing was written beyond MaestroClaw's own expected session-log instrumentation (`git status`/`git diff` diffed against a re-baselined snapshot after each adapter, not just "assume clean").
- **Two adapters, two different enforcement mechanisms, run side by side, deliberately:**
  1. **`claude_code` (task mode)** — read-only because `--dangerously-skip-permissions` is never passed in task mode; Claude Code's own default permission model denies unresolvable write/edit requests in non-interactive mode.
  2. **`codex_cli` with a new `{ sandbox: "read-only" }` constructor option** (`src/adapters/codex-cli.ts`) — read-only enforced by Codex's own OS-level sandbox (Landlock/seccomp/Seatbelt/native Windows sandbox), a stronger guarantee than a permission model. Deliberately a **constructor option, not an env var** like the other adapters' model overrides: sandbox mode is a per-job decision (some jobs want `workspace-write` to generate code, some want a verifiable `read-only` review), not a worker-wide one — `adapters/index.ts`'s registry keeps constructing `CodexCliAdapter` with no args (unchanged default `workspace-write` for every existing caller); a caller needing a different mode (like this script) instantiates the adapter directly.
- **Uncommitted-content handling, logged transparently:** `votd_calendar.json` turned out to be untracked (`git status` shows `??`) in the source repo — real, current draft content that simply hasn't been committed yet. A plain `git clone` doesn't see it (the same way a real hosted job cloning from a `repo_url` over the network never would see someone's uncommitted local changes — this is inherent to cloning, not a MaestroClaw gap). The script copies that one file explicitly (a read of the source, a write only into the already-disposable clone) and logs that it did so, rather than silently reviewing stale/absent content.

### Critical finding along the way: codex_cli has been broken since Sprint 1

Building the `{ sandbox: "read-only" }` option and running it for real surfaced a regression in my own earlier Sprint 1 work: `codex exec --sandbox <mode> --ask-for-approval never` **fails to parse at all** on the actually-installed Codex CLI (0.147.0) — `error: unexpected argument '--ask-for-approval' found`. `-a/--ask-for-approval` is a flag on the root `codex` command, not on the `exec` subcommand; placing it after `exec` (as Sprint 1 did, following Sol's citation-backed but not empirically-verified research) is a hard parse error. This meant **every real `codex_cli` task/session invocation has been failing outright since Sprint 1 shipped** — it type-checked clean and passed every existing test, because nothing in the test suite actually invoked the real `codex` binary.

Fixed: `--ask-for-approval never` removed entirely from `codex-cli.ts`'s exec invocation. Confirmed empirically (via the exec-mode startup banner) that this isn't a loss of functionality — `codex exec` is non-interactive by construction and already defaults to `approval: never` on its own; there was nothing to configure. Both sandbox modes (`workspace-write` default, `read-only`) now verified working against the real installed binary.

**Added `test/codex-cli.test.ts`** — the first test in the suite that invokes the real installed CLI rather than testing pure logic, specifically because this exact bug class (compiles clean, passes every unit test, still completely broken against the real binary) is invisible to unit testing alone. Skips gracefully (not fail) if `codex` isn't installed on the machine running the suite.

This is the same lesson as the `;`/cmd.exe finding one level deeper: **verify empirically against the real installed binary, even when a fix is citation-backed and even after it's already shipped and tested** — a good citation describes what the software does; only running it confirms what it does *right now, on this argv shape, on this version*.

### Result

Both adapters succeeded. Read-only verified clean for both (zero unexpected writes — only MaestroClaw's own expected session-log instrumentation appeared, confirmed via before/after `git status` diffing, not just trusting the sandbox/permission claims). Full outputs saved to the scratch directory printed at the end of each run (copied into this session's scratchpad for persistence: `claude_code-task-mode.md`, `codex_cli-sandbox-read-only.md`, `prompt-used.md`).

Both reviews were independently generated (never shown any existing manual review) and were substantively comparable in depth and specificity to the manual `FABLE-REVIEW-votd-calendar-72-entries.md` / `SOL-AUDIT-votd-calendar-*.md` files already in the Eliana repo from tonight's hand-run council process — real cross-cutting pattern findings (templated "Carry It With You" openers, "Why It Matters" restating "Notice This" instead of extending it, chain entries spoiling their own later payoff), entry-by-entry critique with specific proposed fixes, not generic praise.

One finding was genuinely new, not just independently convergent: `codex_cli`'s review flagged that Entry 9's practice ("consider whether it might be God's means of preserving you") risks encouraging a reader to interpret abuse, illness, or institutional mistreatment as divinely-assigned confinement to passively endure — a real pastoral-care risk. Checked against all three existing manual review files (`FABLE-REVIEW`, both `SOL-AUDIT` passes) covering this exact entry: **none of them raised this.** This is a concrete, checkable instance of the same "measurable, non-redundant" result Michael described from tonight's manual council work — produced through MaestroClaw's actual job/adapter pipeline, not a hand-run CLI call.

### What this proves, and what it doesn't yet

**Proves:** the adapter-execution core (real adapters, real clone-into-ephemeral-workspace pattern, real prompt → report flow) works for a genuinely different task shape than code generation, produces comparable-or-better review quality to manual work, and can be made verifiably read-only through either of two independent mechanisms.

**Doesn't yet prove:** nothing about the live hosted queue (web submit → executor-api → MaestroClaw claim → report-back) — untouched by design, see above. Nothing about the 62 remaining VOTD entries or the ALIYAH-ASCENT-DRAFT modules — this was a small, bounded first slice on purpose. Nothing about council/deliberation orchestration (multiple models cross-reading each other, anonymized peer review, synthesis) — that's the web/edge layer's job per §1's architecture, not MaestroClaw's; this proof workload only exercised one adapter at a time, independently, which is what "read-only retrieval, not council orchestration" always meant.
